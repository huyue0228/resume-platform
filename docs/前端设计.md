```
┌────────────────┬──────────────────────────────────────────┐
│ 深色固定侧栏    │ 白色顶栏               [用户 / 角色 ▾] │
│ ▣ 海纳智聘      ├──────────────────────────────────────────┤
│ DashBoard       │                                          │
│ 处理任务        │                                          │
│ 数据管理 ▾      │                                          │
│   · 简历库      │            浅灰内容区                    │
│   · 岗位需求    │      (PageContainer / ProTable)          │
│   · 院校清单    │                                          │
│   · 部门接口人  │                                          │
│ 系统设置 ▾      │  ← 接口人身份时仅显示有权访问的菜单         │
│   · 配置项      │                                          │
│   · AI 模型连接 │                                          │
│   · Prompt 管理 │                                          │
│   · 用户权限    │                                          │
└────────────────┴──────────────────────────────────────────┘
```

> 当前结构：
> 1. **数据导入入口在各数据页内**：简历→简历库、岗位→岗位需求、院校→院校清单、接口人→部门接口人；四类导入弹窗内均提供对应的 v1 标准模板下载。
> 2. **处理由上传和处理简历触发**：两种入口都要求用户选择本次 Rule / AI 模式并只创建一条任务；上传从 Step1 开始，“处理简历”从 Step2 院校分类/准入开始，Rule 止于 Step3，AI 继续 Step4。Rule 始终可选，AI 仅在当前模型连接测试有效时可选。
> 3. **所有数据表格支持列宽拖拽，可筛选业务列支持表头筛选**：可独立查询的列表采用后端分页，表头文本、单选/多选和日期区间筛选参数进入接口查询；共享分页主表默认提供每页 `10 / 20 / 50 / 100 / 500` 条选项，`page_size` 最大 500，调用方显式分页配置仍可覆盖。导出全部按当前筛选条件执行；日期区间支持清空、单边或双边输入。简历详情内嵌表格不提供筛选器。简历库主表不设操作列；其它页面保留的操作列可调整宽度，但不提供筛选器。
> 4. **`DashBoard` 是置顶首页**：路由仍为 `/analytics`，不属于“数据管理”子菜单；管理员和 HR 登录后默认进入该页，未获 `analytics.view` 权限时整个导航项隐藏并进入首个有权页面。
> 5. **侧栏分组可独立展开或收起**：「数据管理」和「系统设置」分别维护展开状态；点击某个子页面只更新当前选中路由，不应自动收起其它已展开分组。
> 6. **处理任务是独立导航与页面**：路由 `/processing-tasks` 由 `pipeline.view` 控制，位于 `DashBoard` 之后，不再占用顶部栏或以 Drawer 展示；取消活跃任务仍要求 `pipeline.run`。
> 7. **Prompt 管理是独立系统设置页面**：路由 `/prompt-management` 与全部操作复用 `settings.manage_ai_connection`；无权限时菜单被过滤，直接访问也跳回首个有权页面，接口仍由后端返回 403。
> 8. **页面使用频率是布局级静默埋点**：只跟踪登录后白名单业务路由，不新增侧栏菜单、Grafana 配置页或项目内使用频率看板。
> 9. **前端不感知 Agent 网络拓扑**：即使启用独立二进制 Kernel，浏览器仍只访问 Django `/api/*`；不保存或调用 Agent host、HMAC、mTLS、API Key，不直接发送简历、Prompt 或工具请求。Kernel 升级不能要求同步发布前端。
> 左侧菜单**按权限码和数据范围显示**：简历库是候选人查看、部门下发、部门转派和反馈的统一入口。HR/管理员查看全量；二级接口人看到本二级部门及其三级子部门收件箱，三级接口人只看到本人三级部门收件箱。

当前共享实现：

- `SmartDataTable.jsx` 统一提供列宽拖拽、列设置、文本/选择/日期区间的服务端或本地筛选、行点击隔离和服务端分页默认选项 `10 / 20 / 50 / 100 / 500`；日期区间序列化时分别提交起止参数，清空任一端仍保留另一端。简历库主表及岗位、院校、接口人、用户权限和配置表按列启用筛选，简历详情的投递志愿、分配尝试和 AI 筛选决策表不配置筛选器。
- `ImportButton.jsx` 统一在四类导入弹窗内提供“下载标准模板”，按当前业务类型调用 `GET /api/import/templates/{template_type}/` 并保存后端中文文件名；下载失败和导入表头校验失败都沿用统一 API 错误提示。
- `ResizableHeaderCell.jsx` 负责表头拖拽手柄和 pointer 事件；样式类 `.srf-column-resize-handle` 定义在全局 CSS。
- `SchoolTagBadge.jsx` 统一渲染院校标签，根据完整标签名称生成稳定区分色；同名标签同色，不同标签使用不同颜色，简历库、候选人详情、院校清单、院校标签字典和准入规则保持一致。
- `ResumePreview.jsx` 负责 PDF/文件预览，PDF 通过鉴权 API 取得 Blob 后交给 PDF.js 渲染到 canvas，不依赖浏览器原生 PDF 内嵌能力；组件支持未选择、加载中、失败提示、分页、新窗口打开和“下载原文件”；可按 `resume` 直接预览，也可按 `attemptId` 走分配尝试数据范围预览。无权限或越权时不展示下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。
- `ResumeExportModal.jsx` 统一承载候选人级和尝试级简历导出的属性选择。弹窗从 `/api/candidates/export-fields/` 获取版本 3 的候选人、当前投递、岗位需求、分配反馈、状态与原因五组字段目录；目录加入部门收件箱、结构化反馈原因和处理时效字段，不含 `processing_result`。弹窗提供全选、清空、恢复默认和已选数量，并增加“同时下载简历原件”复选框。每次打开都默认不勾选，不写入 `localStorage`；此时说明仅下载按候选人汇总且不含原件的 Excel，确认按钮显示“导出 Excel”。勾选后说明 ZIP 包含 Excel 与原件，按钮切换为“导出 ZIP”。未选字段、目录加载失败或正在加载时禁用当前确认按钮。用户确认后仅按 `srf.resume-export-fields:<user id/username>` 将目录版本和稳定字段键保存到 `localStorage`；重新打开时过滤 `processing_result` 等失效字段，剩余有效选择为空、JSON 无效或存储不可用时使用后端默认字段。勾选顺序不影响提交和 Excel 列顺序。
- 前端 API 封装位于 `src/api/services.js`：除 W3 登录、开发令牌校验、预览、导出和候选人维护封装外，Prompt 管理使用 `fetchAIPrompts / saveAIPromptDraft / resetAIPromptDraft / testAIPromptDraft / publishAIPromptDraft / fetchAIPromptVersions / fetchAIPromptVersion / restoreAIPromptVersion` 对应初始化、共享草稿、真实测试、发布、历史详情和恢复接口。
- 全站登录后界面统一使用浅灰背景、低阴影白卡、靛青主色、深色固定侧栏和白色顶部栏；`ConfigProvider`、ProLayout token 与全局 CSS 统一 Card、Table、Tabs、表单、Drawer 和 Modal 的视觉。`/login` 不再承载用户名密码表单或普通登录按钮，正常状态只短暂显示跳转状态并自动进入 W3。
- `AnalyticsPage.jsx` 通过 `fetchRecruitmentOverview` 只读取后端聚合数据，使用 Ant Design 卡片和 Chart.js 环图/横向柱图展示，不下载候选人明细自行统计。
- 登录后 `BasicLayout` 监听白名单业务 `location.pathname`，忽略 query/hash。初次进入、刷新、路由切换和 `window.focus` 都为当前页生成新事件 UUID 并静默调用 `POST /api/analytics/usage/page-view/`。会话 ID 与最近上报活动时间分别保存在 `sessionStorage` 的 `srf.usage-session-id / srf.usage-last-activity-at`；距上次活动达到 30 分钟则换新会话 UUID。上报失败不抛到全局错误处理、不弹提示、不阻断路由或业务请求。
- 主布局为拥有 `pipeline.view` 的用户提供独立“处理任务”页面，该权限默认授予 HR/管理员；页面约每 2 秒轮询并支持手工刷新。任务卡按 Step1–Step4 展示阶段和耗时，主结果固定为处理完成、需处理、失败、跳过、取消；AI 的待复核、待下发、建议归档是处理完成子项。非零结果跳转 `processing_result=<completed|needs_attention|failed|skipped|cancelled>`，旧 success 链接仅兼容；取消按钮另按 `pipeline.run` 控制，并保留并发审计交互。

- AI 任务卡额外展示 `ai_effective_concurrency / ai_concurrency_limit`、模型重试数和 429 限流数；所有任务统一展示 completed、needs_attention、failed、skipped 和 cancelled 计数。

- **目标 Agent 展示（未实现）**：AI 任务卡在后端返回相应字段时增加主执行引擎、执行模式、主 Agent build、protocol/toolset/policy 版本、只读模型连接 revision、当前阶段、模型回合数和工具调用数；不轮询二进制。若有 shadow，另显示“旁路对照”lane 及其独立 build/revision/状态，不把 shadow 成败并入任务业务计数。运行详情中的 SafeTrace 只对全量数据范围的 HR/管理员且拥有 `pipeline.view` 时展示为脱敏时间线，不显示 Prompt、完整简历、模型原响应或隐藏思维链。`shadow` 明确标记“影子结果，不影响业务”，`review_only` 明确标记“正向下发和负向归档均须人工复核”，不把二进制 completed 误显示为业务已提交。

W3 唯一入口交互：

- `/login` 没有用户名/密码表单。无 W3 回调参数时，`LoginPage.jsx` 请求 `GET /api/auth/w3/status/`；`ready=true` 且 `start_url` 有效时立即自动导航到后端 W3 授权入口，不要求用户再次点击。加载期间只显示“正在跳转 W3”，不得闪现用户名、密码或测试账号。
- 状态请求失败时显示最小错误说明和“重试”操作；`ready=false` 且 `debug_token_login_enabled=false` 时显示 W3 尚未正确配置。只有服务端明确返回 `debug_token_login_enabled=true`（即 `DEBUG=True` 且 W3 未就绪）时，才显示“开发令牌”密码样式输入框、“使用开发令牌登录”和“重新检查 W3 登录”，不展示用户名字段，也不调用已删除的 `POST /api/auth/login/`。
- 自动跳转只使用后端返回的固定 `start_url`，前端不构造 authorize URL，不接受或转发用户传入的 `redirect`/`next`。后端回跳只返回服务端配置且校验过的本站相对地址，路径必须精确为 `/login`，可携带服务端固定查询参数，但不得预置 `oauth2` / `oauth2_error` 保留键，也不得携带 URL params 或 fragment；绝对 URL 不允许，因此前端不形成开放重定向。
- 回跳登录页仅识别 `oauth2=success` 和 `oauth2_error=<stable_code>`。成功时 `RoleContext` 调用 `POST /api/auth/w3/complete/` 一次性领取后端经 Django Session 保存的项目 DRF Token，再沿用现有 `localStorage` 和 `/api/me/` 初始化逻辑。URL 不携带 W3 Access Token 或项目 Token；重复/过期领取显示后端错误并要求重新登录。
- 开发令牌提交时，`RoleContext.loginWithDevToken()` 先使用临时 `Authorization: Token <令牌>` 请求 `/api/me/`；只有成功取得当前用户后，才通过统一 `applyLogin()` 写入 `srf_token` 和用户状态并跳转首页。空令牌不能提交，校验失败显示后端错误或“开发令牌无效或账号不可用”，不得残留令牌或伪造登录态。
- `state_invalid / provider_denied / authorization_code_missing / token_exchange_failed / userinfo_failed / employee_no_missing / email_missing / account_not_found / account_inactive` 在登录页映射为明确中文错误，未知码显示通用“W3 登录失败”。`email_missing` 提示 W3 用户信息缺少有效邮箱；工号和邮箱未同时映射到同一个启用账号，或账号停用时只提示联系管理员，前端不做单字段降级、不自动建号或切换其他账号。
- W3 UserInfo 顶层字段已确认为 `tenantId`、`uuid`、`globalUserID`、`email`、`employeeNumber`；服务端默认用 `employeeNumber` 严格匹配 `User.username`、用 `email` 匹配 `User.email`，`tenantId / uuid / globalUserID` 不参与匹配、不落库，前端也不消费或展示。W3 提供方地址、client 凭据、scope、工号/邮箱字段路径、PKCE 和 redirect URI 等均为服务端环境变量，默认 `W3_OAUTH2_EMPLOYEE_NO_FIELD=employeeNumber`、`W3_OAUTH2_EMAIL_FIELD=email`；前端不提供 W3 配置页、不保存 provider token 或客户端 secret。`POST /api/auth/login/` 已删除；`POST /api/auth/logout/` 和 `GET /api/me/` 交互保持不变。

### 1) 简历库（候选人列表 + 投递详情 + 上传即处理 + 撤销）
```
简历库                       [↥ 上传简历] [▶ 处理简历] [⇩ 下发] [↺ 上传撤销记录]
```

### 3) 候选人处理主流程（随上传/处理简历提交后台任务）

> AI 模式通过真实模型链路处理；未配置可用连接或调用异常时展示后端“需处理”原因和处置入口，只有 `llm_timeout` 展示为“失败”；不得展示 Rule 结果、固定置信度或元数据拼接结论。

```

  Step1 查重与志愿排序
    → Step2 院校分类及学历/院校准入
    → Step3 岗位与分配前置检查
    → Step4 AI 深度筛选与分配（仅 AI）

基础数据：岗位需求、部门、部门接口人独立维护
```
> Step2 完整生成并固化院校标签；Step3/Step4 不再修改。岗位需求和部门应在处理前维护就绪；接口人只决定哪些用户可进入对应部门收件箱，不是创建分配尝试的前置条件。
> 前端提交 `/api/pipeline/run/` 或上传请求后，生产异步环境收到 `202 + processing_runs` 即恢复页面操作；本地 eager 模式同步完成后返回相同字段的 200。每次只创建本次选择模式的一条运行。拥有 `pipeline.view` 的用户通过侧栏独立「处理任务」页约每 2 秒轮询；管理员和 HR 默认拥有该权限，二级、三级接口人默认不展示该导航项。连接配置后续变化不改变已按提交时模式固化的任务。
> **目标 Agent 调用边界（未实现）**：前端提交格式仍只有业务 `mode=rule|ai`，不允许用户随请求指定 Agent host、build、协议、工具集、模型连接 revision、主/shadow lane 或执行模式。Django 按部署兼容矩阵固定唯一主执行引擎，以及可选的一个旁路 shadow；主引擎继续负责业务提交和任务计数，shadow 失败不改变 ScopeItem 或业务结果。AI 不兼容、冻结 revision 不可执行或未就绪时 `/api/allocation-mode/` 返回稳定不可用原因并禁用 AI，Rule 始终可选。Agent 版本灰度、shadow 和 review_only 是服务端发布策略，不在普通处理弹窗中暴露为绕过策略的用户选项。
> 多个 HR 可同时提交任务。提交范围与版本快照已由后端固化；同一候选人的自动任务会等待当前候选人处理租约释放。人工下发、转派、反馈或手动分配会推进流程版本并使在途自动任务令牌失效；版本或令牌不一致时任务显示 `skipped_manual_change`，安全跳过结果且不覆盖人工操作。

### 4) 简历库中的分配尝试
```
简历库                                [处理简历] [下发] [批量转派]
┌ 表头筛选: 当前接收一级部门、当前接收部门、候选人、投递岗位、分配原因
├──────────────────────────────────────────────────────────
│姓名│最高学历专业│投递时间│当前投递岗位│岗位部门│当前接收一级部门│当前接收部门│岗位类别│院校标签│状态│原因│
│张三│计算机      │08-24   │后端工程师  │平台组  │研发体系          │技术部      │研发    │985     │待反馈│岗位与专业匹配…│
├ 勾选后滑入: 已选 N 项｜导出选中/当前筛选｜删除选中｜取消选择
└ 详情展示全部投递、历史尝试、处理时间线、AI 决策、反馈和简历预览
```
> **统一操作台**：简历库主表展示当前有效 `AssignmentAttempt` 的当前接收一级部门、当前接收部门和分配原因；当前应聘ID、当前主体和分配来源保留为默认隐藏列，首次二级部门仅在详情与导出中展示。详情展示完整历史、每次尝试状态和只读处理时间线。HR 进行待复核确认、取消、转人工、下发和部门转派；二级接口人按部门权限转派；当前接收部门接口人提交反馈。
> **AI 决策边界**：岗位精确映射是 Rule / AI 共享服务。Rule 执行专业审核；AI 固定岗位、首次二级部门和 HC，不选择具体接口人。AI 只处理 Step2/Step3 已通过的候选人，不判断学历、院校、志愿、岗位存在性或部门归属。
> **Rule 策略**：只处理当前有效志愿，按“同主体对外职位名称精确映射唯一内部职位 → 同主体内部职位岗位池 → 专业确定性匹配 → 二级部门 → HC 配额”生成待下发尝试。部门没有启用接口人不阻断分配。
> **AI 策略**：AI Step3 使用与 Rule 相同的内部职位精确映射、同主体岗位池和 HC 配额选择，但不做专业词表筛选。模型协议不含岗位或部门 ID；普通 AI 分配使用 Step3 固定岗位和首次二级部门。AI 专项配置改选父级二级部门和固定三级部门，命中后时间线展示两段系统自动路由事件，业务页面仍统一显示 AI 自动分配。
> **AI 并发执行**：生产环境的 Step4 按候选人投递到独立 `ai` 队列并发处理；本地 SQLite + eager 模式仍串行同步执行。
> **目标 Agent 状态边界（未实现）**：处理任务与候选人详情只轮询 Django 保存的 Agent 运行投影。`accepted / observing / reasoning / tool_running / proposing / evidence_check` 展示为 Step4 的子阶段；最终业务状态仍只取主 lane 经 Django Policy/Executor 提交后的 ScopeItem、Decision 和 Attempt，不以二进制 HTTP 200、Agent `completed` 或 shadow 结果单独判定成功。`review_only` 下 Agent 提出的 dispatch 和 archive 都展示为“待复核”，不得直接显示待下发或已归档。
> **分配尝试**：主表支持当前接收一级部门、当前接收部门、候选人、投递岗位、分配来源和分配原因筛选，不展示或筛选尝试状态；详情保留状态、首次部门、当前部门、结构化反馈和事件时间线。接口人只看到部门数据范围内的 `dispatched / passed / rejected` 尝试，不展示 HR 待处理状态。
> **AI 复核操作**：HR 可在 `pending_review` 尝试详情中确认下发、取消或转人工处理；当前完整模型连接配置测试有效时还可重试 AI。分别调用 `confirm-review`、`cancel-review`、`transfer-to-manual` 和 AgentDecision `retry` 接口。取消后若没有其它活动尝试，简历库显示 `agent_no_recommendation` 归档；转人工时必须从该尝试的具体投递进入手动分配，不允许隐式换志愿。**目标 Agent 扩展（未实现）**：review_only 的 dispatch/review-origin 继续展示“确认下发”并显示“已预占 HC”；archive-origin 明确显示“Agent 建议归档、未占 HC”，按钮改为“确认归档”和“改为下发”，不显示含糊的单一确认按钮。确认归档不请求容量；改为下发提交 `decision=dispatch` 后若容量已满，页面刷新为“待重新分配 / HC 已满”，不得仍显示待复核或伪造下发成功。
> **待下发取消**：HR 可取消 `pending_dispatch` 尝试，调用 `POST /api/workflow-attempts/{id}/cancel/`；取消后刷新候选人当前状态和可执行操作。
> **AI 结果边界**：只有 `llm_timeout` 使用“失败”；岗位缺少工作职责、正文不可用、连接/认证、429、输出协议和固定引用失效显示“需处理”；学历/院校/岗位/部门等规则结果显示“处理完成”。其它异常均不自动回退 Rule。
> **详情与预览**：分配尝试详情抽屉展示候选人、应聘ID、岗位、首次二级部门、当前接收部门、状态、反馈原因和备注，并通过权限安全接口预览简历。处理时间线按事件顺序展示创建、复核、下发、转派、反馈和相邻事件耗时，系统自动路由有明确标识。
> **导出**：主表候选人选中和当前筛选导出走 `/api/candidates/export/`，详情中的接口人单条尝试导出走 `/api/workflow-attempts/export/`；三个入口都先打开同一个 `ResumeExportModal`，从候选人、当前投递、岗位需求、分配反馈、状态与原因五组字段中勾选属性，支持全选、清空和恢复默认，未选任何字段时禁止提交。版本 3 默认选择姓名、手机号、当前应聘ID、当前岗位、当前志愿、首次部门、当前接收一级部门、当前接收部门、简历状态和反馈原因，不默认选择分配来源；读取浏览器旧选择时自动过滤失效键。原件复选框每次打开都默认不勾选且不持久化；前端以逗号分隔 `fields` 并显式传递 `include_resume_files=false`，按钮为“导出 Excel”。勾选时改传 `true`、按钮为“导出 ZIP”。前端读取 `X-Export-Mode / X-Export-Count / X-Export-Missing / X-Export-Candidate-Count`：Excel 模式只提示候选人数，ZIP 模式继续提示候选人、成功原件和缺失数。当前筛选、Dashboard 下钻、权限范围和 Excel 固定列顺序不变。
>
> Excel 一名候选人一行；勾选原件时 ZIP 另含 `简历文件/`。字段目录删除二/三级接收接口人，增加首次二级部门、当前接收一级部门、当前接收部门、反馈原因和处理时长。接口人导出仍只基于部门可见尝试，不因选择手机号扩大数据范围。
> **HR 下发操作**：HR 可在详情单条下发，也可使用常驻批量下发；成功后尝试统一显示“待业务反馈”，当前接收部门为首次二级部门。无人部门不阻断下发，通知结果只在事件元数据中体现。
> **单条转派**：详情调用 `transfer-options` 加载允许的二/三级部门，以 `target_department_id + note?` 提交。HR 可转任意二/三级部门；二级接口人仅在拥有 `attempt.transfer_department` 且 `can_delegate=true` 时可转任意二级部门或本人二级部门下的三级部门。转派后状态仍为 `dispatched`，列表、筛选和可见范围立即刷新。
> **批量转派**：选择候选人后打开弹窗即冻结 ID；目标只允许二级部门，备注可选。以 `candidate_ids + target_department_id + note?` 提交 `/api/candidates/bulk-transfer/`，响应使用 `batch_operation_id`，页面展示成功、跳过、失败数量；逐项成功/跳过在 `results`，失败在 `errors`，不因部分失败隐藏成功项。
> **反馈**：反馈按钮按 `attempt.feedback`、`status=dispatched` 和“当前接收部门正好等于本人部门”判断。选择“不通过”后必须从后端固定原因选项中单选，并以 `reason_code` 提交；选择“其他”时备注必填。选择“通过”时隐藏原因并不提交原因码。首次提交成功后结果、原因和备注只读；并发状态变化提示刷新详情。
> **手动强制分配**：HR 从具体应聘ID选择目标二级或三级部门。二级目标进入普通待下发；三级目标展示父级二级部门并在完成后以两段事件进入三级部门，无需选择具体接口人。
> **AI 专项配置与业务展示边界**：专项开关、阈值、父级二级部门和目标三级部门由「AI 模型连接 → AI 专项」配置；专项内部判断仍不进入业务页面。
> **归档候选人**：归档原因、志愿概览和从具体应聘ID发起手动强制分配统一合并到简历库；不再作为 HR 独立菜单入口。
> **角色差异**：二级接口人看到本人二级部门及其三级子部门收件箱，可按权限导出和转派，但只反馈当前接收部门等于本人二级部门的简历；三级接口人只看并反馈本人三级部门收件箱。接口人均无 HR 下发和手动分配权限。
> **断代升级**：前端删除旧的接口人定向转派接口、旧状态映射、旧权限码和旧 AI 专项目标字段，不发双请求、不保留旧参数回退。升级迁移会清理测试阶段流程及上传快照数据，页面按保留的候选人/投递主数据重新处理。

### 5) DashBoard（招聘分析）

- 路由 `/analytics` 和侧栏置顶「DashBoard」导航项由 `analytics.view` 控制；管理员和 HR 默认可见并以该路由作为登录首页，二级/三级接口人默认不可见且按权限进入首个可访问页面；越权路由跳回有权默认页，接口仍以后端 403 为准。
- 页面采用与全站一致的浅灰背景、低阴影白卡和靛青主色。页面不设置独立筛选栏，只在数据展示区左上角内嵌时间区间、一级部门和二级部门三个筛选器；右上角在用户同时拥有 `resume.view` 时显示「导出结果报表」，否则只保留数据截至时间。首屏展示候选人数、分配、下发、反馈、通过五张 KPI 卡，图标固定在卡片右上角，不展示按日趋势图或候选人明细表。
- 看板界面只开放时间区间、一级部门和二级部门筛选；未指定日期时后端默认最近 30 天，页面显示当前实际 cohort 和 `data_as_of`。一级部门选项读取 `filter_options.primary_departments`，二级部门选项读取 `filter_options.departments`，并用每项的 `parent_id` 在选定一级部门后只展示其下属二级部门。接口为兼容既有调用仍可接受招聘主体、岗位、院校标签、最高学历和分配来源参数，但当前页面不展示这些选择器。
- 「导出结果报表」不打开日期或属性选择弹窗，直接读取后端最近一次成功加载并已生效的 `data.filters.date_from / date_to / primary_department_id / department_id`，分别映射为 `imported_after / imported_before / primary_department_id / department_id` 调用 `/api/resumes/result-report/`；用户在筛选控件修改但尚未点击查询的草稿值不能提前影响导出。日期未生效时按钮禁用，下载仍为独立 `.xlsx`，不并入简历组合 ZIP。

- 结果报表的“部门汇总”和“简历明细”统一按八种新简历状态输出；Dashboard 卡片中的“已生成分配”、分类、下发、反馈等仍是独立分析指标，名称和统计口径保持不变。
- 五张核心卡依次展示候选人数、已生成分配、已下发、已反馈和已通过；投递记录/已分类收入候选人数卡辅助信息，已归档收入已通过卡辅助信息。招聘概览使用“分配来源环图 + 候选人/分配/下发/反馈/通过横向流程柱图 + AI 建议环图”的三列布局。
- 页面继续展示既有招聘耗时，并从 `handling_speed` 渲染“人工处理时效”：总体卡读取 `hr_dispatch_hours / department_processing_hours / total_feedback_hours`，各自展示平均值、中位数、P90 和完成样本数，另展示 `pending_count / max_pending_age_hours`；部门表逐行读取 `processing_hours` 及相同待处理指标。自动转出的二级瞬时区段不计人工时长，不提供个人排名。
- 岗位和当前接收一/二级部门排行使用横向柱图；未通过原因按六个固定原因码展示环图和下钻，不再按自由文本备注聚合。

> **部署、备份与恢复边界**：静态运行参数由部署模板预置，浏览器端不提供 `.env` 初始化、备份路径、密钥或 W3 配置页面。首次运行部署脚本生成 `DJANGO_SECRET_KEY / POSTGRES_PASSWORD / RESTIC_PASSWORD / USAGE_METRICS_TOKEN` 四项独立密钥和权限为 `600` 的 `.env`，保留 `.env.example` 的 `W3_OAUTH2_ENABLED=False` 安全占位，然后在任何 Docker 变更前退出；运维必须补齐 W3 参数、把开关改为 true，再第二次运行真正部署。`USAGE_METRICS_TOKEN` 只用于 Grafana 的 `X-Usage-Metrics-Key` 和服务端匹配，不得编译入前端、下发浏览器或写入 `localStorage/sessionStorage`。W3 是可用部署的必要条件，`validate-w3-env.sh` 先强制 `DJANGO_DEBUG=False`，再对 disabled、缺失或非法 W3 开关直接失败，不再跳过。必填变量为 client id、authorize/token/userinfo/redirect 地址、工号/邮箱字段路径、客户端认证方式、请求超时和事务 TTL；字段路径默认 `employeeNumber / email`，basic/post 要求 secret，none 可空，scope 按提供方要求；前端回跳 `/login` 和 PKCE 开启使用安全默认，部署模板不再包含本地登录开关。redirect URI 必须为 HTTPS、精确指向 `/api/auth/w3/callback/` 且不带 params/query/fragment；前端回跳必须指向本站 `/login`，可带非保留固定 query，但不得预置 `oauth2` / `oauth2_error`。错误只在终端输出键名和稳定说明，不显示 secret；`verify.sh` 会重复同一校验。`BACKUP_TARGET_PATH` 默认 `/mnt/smart-resume-filter-backups`，必须是已存在、可写的绝对路径。检测到已有容器或数据卷时，原 Django、PostgreSQL 和 restic 密钥缺失或仍为占位值必须恢复原 `.env`，不得重新生成或替换；旧环境仅缺 `USAGE_METRICS_TOKEN` 时允许补齐且不得轮换其它安全值。备份调度、restic 保留、显式确认恢复（覆盖生产库时二次确认）和隔离演练属于部署运维能力，不在前端新增菜单或恢复按钮；浏览器端不得接收或保存数据库、restic、`DJANGO_SECRET_KEY`、`USAGE_METRICS_TOKEN` 等凭据。
>
> **正式 HTTPS 入口**：生产默认在 Compose frontend 前使用企业网关、WAF、Nginx 或 Caddy 终止 TLS。外层代理把所有路径统一转发到 frontend 暴露端口；frontend 容器内置 Nginx 返回静态页面，并把 `/api` 转发到 `backend:8000`。外层代理不得把 `/api` 直接转发 backend，也不得暴露可绕过 frontend 的 backend 端口。代理必须保留 `Host`，设置 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto=https`；同机反代建议 `FRONTEND_BIND=127.0.0.1`、`BACKEND_BIND=127.0.0.1`，异机网关只通过受控内网/防火墙访问 frontend。
>
> `DJANGO_ALLOWED_HOSTS` 填生产域名，`W3_OAUTH2_REDIRECT_URI` 必须与 `https://<生产域名>/api/auth/w3/callback/` 逐字一致。生产验收从真实客户端网络检查 HTTPS 域名、证书、HTTP→HTTPS 跳转、`/api/auth/w3/status/` 和完整 W3 回调；仅访问服务器 IP、`IP:5173` 或容器健康检查不算完成。

> 二级/三级接口人默认没有 `analytics.view`，登录后通常进入简历库。普通列表和详情响应不包含手机号、其它志愿、其它尝试或 AI 决策；导出候选人、投递和文件仍使用部门数据范围。
> **重要边界**：前端权限配置只负责体验和误操作拦截，不能替代后端鉴权。二级可见本二级子树但只能反馈当前接收部门正好等于本二级的尝试；三级只能查看和反馈本三级部门尝试。

## 四、目标页面清单与当前状态
0. 登录页：路由 `/login`，无回调参数时读取 `/api/auth/w3/status/` 并在 `ready=true` 时自动跳转 W3，不展示 W3 按钮或本地账号密码表单；W3 回跳成功后调用 `/api/auth/w3/complete/` 一次性领取项目 Token。只有 `debug_token_login_enabled=true` 时展示开发令牌输入框，先通过 `/api/me/` 校验才保存；其它错误码、状态请求失败或配置未就绪时展示最小状态/重试界面。URL 不携带 Token，不接受任意回跳参数。
1. `DashBoard`：路由 `/analytics`，按导入 cohort 查看总览、转化、耗时、来源、AI、岗位、一/二级部门和原因分布；页面只在数据区左上角提供时间区间、一级部门和二级部门联动筛选，构成分布采用环图，岗位和两级部门排行采用横向柱图，管理员和 HR 默认可见并作为首页；同时拥有 `resume.view` 时，看板数据项可下钻到简历库，右上角也可按当前已生效的日期及一/二级部门筛选导出结果报表。
2. 处理任务：路由 `/processing-tasks`，独立展示共享任务、阶段、耗时、结果、手工刷新、候选人跳转与取消审计；`pipeline.view` 控制页面和记录查看，`pipeline.run` 控制取消。
3. 简历库：统一承载八状态候选人列表、部门收件箱、AI 复核、下发、单/批量部门转派、结构化反馈、处理时间线、导出和预览。默认列包含当前接收一级/当前部门；当前主体、分配来源、当前应聘ID默认隐藏；当前志愿和具体接口人不进入主表。HR/管理员看全量，接口人按部门范围查看。
4. 岗位需求、院校清单、部门接口人：主数据维护、导入、导入弹窗内标准模板下载、表头筛选和列宽拖拽；岗位需求展示/筛选一至三级部门，支持二级/三级完整路径编辑、停用删除和按当前筛选下载全部启用职位清单；院校与部门接口人既有维护、邮箱同步规则保持不变。WeLink 开关当前不展示、不请求，待真实客户端接入后再恢复。简历信息标准模板下载同样位于简历库上传弹窗内。
5. 配置项与 AI 模型连接：配置项维护院校标签、院校准入、专业词表等业务规则，并为 `settings.manage_config` 提供只含 HC 系数的“分配参数”页签，不再提供任意系统参数编辑；拥有 `settings.manage_ai_connection` 的角色在独立「AI 模型连接」页通过“模型连接”“AI 运行参数”“AI 专项”三个页签维护连接、运行参数及专项开关/阈值/目标链路。连接测试成功后，上传和处理简历时才可选择 AI 模式；专项内部命中、证据和审计不进入业务页面。
6. Prompt 管理：路由 `/prompt-management`，复用 `settings.manage_ai_connection`，整套维护五个固定模块；提供字符限制、共享草稿保存、真实模型测试、原子发布、恢复激活/默认值、只读组装预览、分页历史、模块差异和恢复到草稿。未保存或测试无效时禁止发布，发布只影响新提交的 AI 任务。
7. 用户权限：维护用户、角色、权限绑定和接口人绑定关系，支撑 RBAC 前端配置。
