# 任务中心：创建与查询

## 参考依据

本次参考官方产品文档，复用适合当前平台的交互和状态管理方式。

| 参考 | 成熟产品的组织方式 | 在海纳智聘中的应用 |
| --- | --- | --- |
| [Airflow UI](https://airflow.apache.org/docs/apache-airflow/stable/ui.html) | 计划定义与运行记录分开；运行列表展示状态、触发类型和耗时，可进入单次运行诊断 | 「执行记录 / 定时计划」两页签，执行详情保留阶段、进度、材料与业务结果 |
| [Prefect Deployments](https://docs.prefect.io/v3/concepts/deployments) | 一个任务定义可手动触发、定时触发并暂停后续调度；运行参数属于任务配置 | 统一「处理简历」表单中选择立即、指定时间、每天或每周，保持同一处理范围 |
| [GitHub Actions 运行历史](https://docs.github.com/en/actions/how-tos/monitor-workflows/view-workflow-run-history) | 从工作流定位历史，再按运行进入任务与步骤详情 | 从计划查看全部执行历史，执行详情可通过地址直接打开 |

平台目前只有固定的简历处理流程，继续使用 PostgreSQL 持久化队列和 Go 调度器即可。此次增加创建、查询和计划管理能力，没有引入通用 DAG 编辑器或新的编排服务。

## 创建

简历库保留一个「处理简历」入口，任务中心使用同一表单。填写可检索的名称（选填），选择范围和执行安排，提交前检查摘要。

- 固定候选人：打开表单时冻结勾选的 ID；范围不随表格改选而改变。
- 按状态：沿用打开表单时的表格筛选条件；立即和定时执行保持相同条件。定时触发时重新匹配，后续符合条件的新简历可以进入范围。
- 任务中心创建默认选择「待处理」；需要精细筛选或指定候选人时从简历库创建。
- 立即执行提交后进入队列；指定时间、每天、每周形成定时计划。时间统一使用北京时间 UTC+8，每周沿用首次日期的星期。
- 提交超时仅提示先查询确认，不自动重发。已生成的执行记录保留当次名称、范围和计划来源。

## 查询

「执行记录」默认列表，可切换卡片。支持名称/编号/创建人工号搜索、我创建的、精确状态、触发来源、创建日期，以及计划关联历史；每页 20 条。概览按当前搜索、来源、日期、创建人和计划范围统计全部记录，点击概览筛选进行中、需关注或已结束。需关注是已结束记录中的子集。

筛选在数据库内完成，分页后才展开当前页的阶段与进度。查询条件、页签、页码、展示方式和详情 ID 保存在 URL；打开或复制地址可以还原查询。运行中每 2 秒更新，空闲时每 15 秒更新；切换条件或卸载时取消旧请求，旧响应不能覆盖新结果。

「定时计划」支持名称/编号/创建人搜索、计划状态、频率、创建日期和我创建的筛选，显示范围、首次/下次时间、最近触发结果，并可查看该计划的全部执行记录。空范围、重叠跳过等尚未生成执行记录的情况显示在最近触发说明中。

单次执行详情通过 `run_id` 直接查询，不依赖当前列表是否包含该记录；详情运行中自动刷新，可定位对应的候选人和业务结果。

## 计划操作与边界

- 暂停：停止后续触发，不中止已经生成的执行。
- 恢复：每天/每周计划沿原时刻计算下一次未来时间，暂停期间不补跑；一次性计划已错过时间则恢复后进入下一轮调度。
- 取消：永久结束后续触发，保留计划与执行历史。调整范围或时间时取消原计划并重新创建。
- 非人为暂停导致服务停机时，恢复后仍按既有规则合并补跑一次；上一轮未结束时跳过本轮。
- 创建及触发需要 `pipeline.run` 和 `resume.view`；查看需要 `pipeline.view`。创建人及有处理权限的管理员可管理计划，执行时重新检查创建人权限。

## API

- `POST /api/pipeline/run/`：可附加 `name`；立即创建执行，其余既有 `step/scope` 行为保留。
- `GET /api/pipeline/runs/`：`search`、`state=active/attention/finished`、`status`、`source=manual/schedule/resume_import/ai_retry`、`schedule_id`、`mine=true`、`created_by`、`created_from/created_to`、`page/page_size`、`ordering`；`include_summary=true` 附加全范围统计。
- `GET/POST /api/pipeline/schedules/`：创建正文 `{name, run_at, repeat, scope}`；查询支持 `search/state/repeat/mine/created_by/created_from/created_to/page/page_size`。
- `created_by` 保留用户 ID 语义；精确按工号查询使用 `created_by_username`。执行记录继续支持 `id/ids/step/mode/current_stage` 等已有筛选。
- `POST /api/pipeline/schedules/{id}/pause/`、`resume/`、`cancel/`：加行锁修改计划状态，与触发领取串行化。

## 验证范围

数据库集成测试覆盖分页、全范围计数、北京时间边界、名称和来源查询、范围保存、暂停/恢复、权限及原有并发去重与事务重试。前端测试覆盖统一创建、URL 查询恢复、计划历史与详情跳转、旧请求取消和过期响应隔离。合成测试与浏览器验收不替代真实模型或生产负载验收。

## 志愿生命周期与续处理

- 每个志愿独立保存处理状态、终止时间和流转事件。候选人分组由当前流程统一决定；导入的「应聘状态」仍作为外部原始信息保留，不充当系统处理状态。
- AI 明确不通过当前志愿：保留该志愿的评估和原因，在同一执行、同一候选人任务项内继续下一志愿。下一志愿重新固定唯一投递标准和标签字典；已完成结果与续处理快照在同一事务提交，重启后接续。
- AI 达到入池阈值：直接入池并保存资格，不再经过人工复核。范围启用 execute_v1 后，由独立分配任务按标签、优先级及需求供给分配，HC 只作计划人数；legacy 范围保留原规则。标签暂无匹配时保留入池待分配；材料或模型异常需要处理，不会计为志愿不通过。
- 部门不通过：结束当前志愿，关闭当前入池记录并释放该尝试的容量占用。有未结束志愿时，候选人回到「待处理」，等待下一轮定时任务；反馈接口不创建处理任务。HR 也可通过现有「处理简历」入口手动启动下一轮。
- 所有志愿均不通过：候选人进入「人才库」。普通批处理、固定 ID 定时任务和强制重处理参数均不会覆盖人才库或已通过结果。人才库后续策略尚未实现；将来需建立新的评估轮次，保留本轮结果。
- 「处理简历」按当前进度继续，不再因选择状态或勾选候选人而隐式强制重跑。旧定时计划即使保存了强制参数，也遵守当前阶段。待下发和部门处理中保留当前阶段；入池待分配可复用已有评估尝试分配。已终止志愿不能通过旧 AI 决策重试或手工分配入口恢复。
- 定时计划的范围建议选择「待处理」，并核对原有姓名、岗位、日期等筛选条件，以免排除退回候选人。本次升级不会自动创建或修改计划。

升级新增 `platform_applications` 和 `platform_application_events`，不删除原有评估、分配、反馈记录。迁移依据已有记录补充各志愿当前状态快照，并将原 `all_rejected` 归档分组映射到人才库；迁移事件明确标记来源，不伪造完整历史过程。候选人详情新增志愿状态与流转历史；部门接口人仍仅看到其权限范围内的志愿及部门反馈状态。

取消待复核阶段后，只保留「AI 入池阈值」（沿用 `ai_dispatch_threshold`，默认 0.75）；旧复核阈值不再参与判定。升级时，旧待复核入池记录按当时保存的分数和入池阈值继续处理：达标转待分配，未达标结束当前志愿，历史信息不足转重新评估。原评估和流转记录不覆盖，迁移追加事件；旧待复核分配撤销并释放容量，返回待处理重新判定。旧复核操作接口返回 410。旧计划中的 `pending_review` 筛选兼容为待处理和入池待分配，其他条件仍然生效。

任务中心新增「分配任务」页签，展示范围模式、需求接收状态、供给和方案；不合并筛选与分配的失败状态。详见 [双 Agent 分配运维](two-agent-allocation.md)。
